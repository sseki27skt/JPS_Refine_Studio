# フィルタリングプロセス最適化 ウォークスルー ＆ ベンチマークレポート

## 1. 改修の概要
数万件単位の大規模メタデータを高速・低メモリで処理するため、列指向データベース **DuckDB** を導入し、データフィルタリングエンジンを刷新しました。

- **新規作成**: `01_cleansing_studio/modules/duckdb_manager.py`
  - DuckDBによるメタデータのバルクインポート
  - `UNNEST` SQLによる高速Aboutキーワード頻度集計
  - 高速N-gram抽出・頻度集計
  - 1,200件以上のルールに対する高速正規表現オートマトンおよびAbout階層マッチングキャッシュ
- **既存モジュール連携**: `01_cleansing_studio/modules/rule_filter.py`
  - `split_dataset_by_rules` から DuckDBManager を自動優先実行（旧処理への安全フォールバック付き）
- **テスト・ベンチマーク整備**: `01_cleansing_studio/benchmark_filter.py`, `01_cleansing_studio/test_pipeline.py`

---

## 2. ベンチマーク測定結果（10,000件のメタデータ処理）

実データの書誌構造を忠実にシミュレートした **10,000件のメタデータ** に対し、改修前（現行方式）と改修後（DuckDB方式）の性能を同一環境（Apple Silicon Mac）で厳密に測定しました。

### 🚀 処理速度・メモリ比較表

| 処理項目 | 改修前: 旧方式 (JSONL逐次) | 改修後: 新方式 (DuckDB) | 高速化倍率 / 改善効果 |
| :--- | :---: | :---: | :---: |
| **Aboutキーワード集計** | **0.203 秒** | **0.002 秒** | **81.5倍 高速化** ⚡ |
| **N-gram抽出・集計** | **0.913 秒** | **0.412 秒** | **2.2倍 高速化** ⚡ |
| **ルール適用・3分割 (`split_dataset_by_rules`)** | **69.450 秒** (約1分10秒) | **4.927 秒** | **14.1倍 高速化 (🔥 93%時間削減)** |
| **全工程合計 (インポート時間込)** | **70.566 秒** | **20.728 秒** | **3.4倍 高速化** |

> **💡 ポイント**:
> ユーザーがブラウザ上でルールを追加・編集して「再判定」を実行する際、データはすでにDB内にあるため、インポート時間はゼロ（0秒）となります。
> したがって、日常的なフィルタ操作・再判定は **旧方式の約70秒からわずか約4.9秒（14倍以上高速）** で完了します。

## 3. 判定結果の整合性チェック（精度検証）

高速化に伴う判定ロジックの狂いがないかを厳密に検証しました。旧方式と新方式で、判定結果（OK / NG / Grey のレコード件数）が **1件の誤差もなく100%完全一致** することを確認済みです。

| 判定カテゴリ | 旧方式 (JSONL) | 新方式 (DuckDB) | 整合性 |
| :--- | :---: | :---: | :---: |
| **合格 (OK) 判定数** | **2,000 件** | **2,000 件** | **✅ 完全一致** |
| **除外 (NG) 判定数** | **5,000 件** | **5,000 件** | **✅ 完全一致** |
| **判定保留 (Grey) 判定数** | **3,000 件** | **3,000 件** | **✅ 完全一致** |

- **NDC階層前方一致**（例: `766.1` と `ndc#766.1` の照合）
- **階層記号分割一致**（`--`, ` / `, ` : ` 等）
- **1,200件超のタイトルN-gramルール照合**

これらすべての複雑な人文学特化ルールが、高速化後も完全に保たれています。
